# LadingLens — Roadmap / Deferred Work

Every item below has a specific root cause and a specific production fix path — not just "future work" as a catch-all. Grouped by pipeline layer.

## Bronze extraction limitations

**STLA (Stellantis), DELL, INTC, EMR — 10-K/20-F extraction fails entirely.** Root cause differs by filer:
- STLA's 20-F has zero repeated "Item N" heading occurrences in the visible body text (the real Risk Factors prose exists in the document but has no literal anchor text a regex can latch onto). Requires DOM-aware HTML parsing (e.g. BeautifulSoup on heading tags/styling) rather than a regex tweak.
- DELL/INTC/EMR are US 10-K filers whose Item 1A extraction produces content below the 5,000-char threshold — a filer-specific document-format quirk not diagnosed further.
- Production path: a DOM-aware parser (or a paid extraction API — sec-api.io was evaluated and rejected in Phase 2 for requiring a paid key beyond a small free tier) as a fallback when the regex-based extractor's output is empty or below threshold. Estimated effort: 1-2 days to build and validate against all 4 filers.

**LULU, MU — genuinely contaminated 10-K text (confirmed, distinct from NKE/WMT below).** Both still contain literal audit-firm names (Ernst & Young, Deloitte, etc.) in their extracted `item_1a_text`, confirmed via direct keyword search. Root cause: `ITEM_1A_START` matches many times throughout each document's body (not just the Table of Contents) because these filings cross-reference "Item 1A" repeatedly in later sections (MD&A, legal proceedings), and the extraction algorithm's "pick the globally longest candidate span" heuristic locks onto a spurious mid-sentence cross-reference as the start instead of the true section heading. Broadening the end-boundary regex (the fix that worked for 9 of the 13 originally-contaminated filers in Phase 7) cannot fix this — the bug is in *start* selection, not the end boundary. Production path: rework the start-selection heuristic to prefer the first start match above a minimum span length over the globally-longest one, or move to DOM-aware parsing. Deferred specifically because a quick fix risks regressing the 21 filers that currently extract correctly. Estimated effort: 0.5-1 day, plus a full regression pass against all 24 filers.

**NKE, WMT — a different, milder issue: Item 7A leakage, not audit-firm contamination.** Confirmed via direct check: neither contains an audit-firm name anywhere in `item_1a_text`. Both still carry some Item 7A (Quantitative and Qualitative Disclosures About Market Risk) content past the intended Item 1A boundary — verified by inspecting the tail of each extracted text (e.g. NKE's text ends mid-interest-rate-hedging table). This degrades retrieval relevance for supply-chain/trade-policy queries specifically (confirmed in Phase 7's smoke test: Q2/Q3 targeting these tickers returned financial-metrics content instead of on-topic language) but is not the same failure mode as LULU/MU. Production path: same start-selection rework as above would likely fix this incidentally, since it shares the root cause; not independently prioritized.

**Bronze HS regex false-positive on P.O./reference numbers.** A handful of regex-extracted HS codes (e.g. the Welch's fruit-juice rows found in Phase 5) are actually fragments of purchase-order or document reference numbers that happen to look like HS codes. Production path: require an explicit "HS"/"HTS" prefix keyword with a word boundary before accepting a regex match, rather than matching any digit-shaped substring. Estimated effort: a few hours plus a re-run of the Phase 4 regex-extraction population to check for regressions.

## HS classification limitations

**Short-input embeddings under-encode single-word product descriptions.** General-purpose sentence embeddings (e5-base-v2) perform worse on inputs like "MACARONI" or "BMW" than on full sentences — there's less context to encode. Production path: hybrid retrieval combining the existing embedding similarity with BM25 (or similar sparse lexical) scoring, so short/generic inputs still get a usable signal from exact or near-exact term matches.

**LLM refusal rate 0/4 on the ambiguous eval-seed rows.** The classifier's conservative-refusal instruction (predict `999999` when a description is too vague) never fired on any of the 4 seed rows explicitly labeled ambiguous — it always guessed a specific (wrong) code instead. This may actually be closer to real customs-broker behavior (brokers pick a best-guess code rather than refuse), so it's not unambiguously a defect, but it does mean the refusal rate can't be trusted as a quality signal in its current form. Production path: prompt hardening with explicit vagueness examples, trading classification coverage for precision on the genuinely ambiguous tail. Estimated effort: a few hours of prompt iteration plus re-running the eval seed.

## Entity resolution

**Walmart consignee resolution gap.** Every consignee name matching "WALMART" or "WAL-MART" in this dataset tops out at 29 total shipments — the closest name match, "STARPLAST USA LLC (FOR WALMART)," is a third-party packaging vendor shipping on Walmart's behalf, not Walmart's own import operation. Walmart's real US import volume does not appear to be resolvable from this dataset under any name-matching strategy tried. Production path: cross-reference FMC (Federal Maritime Commission) importer-of-record filings or a commercial customs-data provider that resolves ultimate consignee beyond the raw BoL name field, which this NIST FEIII sample doesn't capture. Estimated effort: depends entirely on data-source access; not a code fix.

**Cross-prefix ER variants (~10-20% projected recall loss).** Entity pairs that don't share the first 8 characters after normalization (e.g. MERCEDES-BENZ vs. DAIMLER MERCEDES) never enter the same blocking key and so are never compared at all. Production path: a secondary blocking pass using coarse embedding clusters (not just name-prefix) to catch cross-prefix variants. Documented as a deliberate scope boundary for this build, not an oversight — production ER systems typically implement this as an explicit second matching pass.

## Concentration analysis

**HHI based on shipment counts, not weight or value.** `shipment_value_usd` is NULL for 54.5% of `fact_shipments` rows, and weight data is comparably sparse — count-based HHI was the only aggregation that could cover the full population without silently dropping the majority of shipments. Production path: revisit once/if the underlying BoL data source provides more complete value/weight fields; the shipment-count HHI is a defensible interim metric (it measures concentration of shipment *events*, which is itself meaningful) but a production system serving real risk decisions should use value-weighted concentration once the data supports it.

**Concentration Heatmap's 10-K drill-down has near-zero practical coverage.** Discovered during Phase 10 demo-script preparation: the heatmap's ticker-link feature is restricted to `exact`-confidence `dim_ticker` matches (a deliberate Phase 9 correctness decision — `partial` matches include confirmed false positives like HPQ matching "FORD MOTOR COMPANY (HP05A)"). But none of the 4 exact-match tickers (DE #148, PH #830, LEVI #13,315, RL #30,636 by shipment-count rank) are anywhere near the heatmap's top-30-by-volume consignee list, so the 10-K expander will show "no confidently-matched filer" for every consignee actually selectable in the current UI. The underlying data problem (few of the 24 indexed SEC filers are also high-volume BoL consignees) isn't fixable by better string matching. Production path: either broaden the indexed-filer set to include more high-volume consignees' parent companies, or decouple the heatmap's consignee list from "top 30 by volume" to also surface exact-ticker-matched consignees regardless of rank. Not fixed in Phase 10 per the "don't touch Streamlit code" scope constraint for this phase; the demo script routes around it by using the Agent Chat panel (which isn't restricted to exact matches) for the 10-K-retrieval story instead.

## Cortex Agent

**p95 latency of 93s is meaningful friction for interactive use.** Fusion queries chaining multiple tool calls take 40-90+ seconds. Production path: reduce tool round-trips (e.g. a combined tool that does structured lookup + scenario simulation in one call instead of two agent turns), or cache frequent/example queries. Estimated effort: a focused optimization pass, likely 1-2 days to meaningfully move the p95 number.

**No streaming response.** `DATA_AGENT_RUN` (the SQL function used throughout this build) returns only after all tool calls complete; Snowflake's REST API for Cortex Agents does support streaming, but adopting it means moving off the simple SQL-function invocation path this project used throughout. Deferred as a larger integration change, not a quick fix.

**Cortex Analyst standalone API unavailable on this account tier, despite Cortex Agent's embedded use of it working fine.** Documented as a finding, not a limitation to fix — see `docs/architecture.md` for the full explanation of why these are gated independently.

**Two confirmed Cortex Agent `generic` tool platform limitations**, both worked around rather than "fixed" (they're account/product limitations, not bugs in this codebase): it rejects object/VARIANT-typed parameters, and independently cannot invoke a `RETURNS TABLE` stored procedure. `SIMULATE_TARIFF_SCENARIO_AGENT` (scalar params, `RETURNS STRING`) exists specifically to work around both. If Snowflake lifts either restriction in the future, the agent-facing wrapper procedure could be retired in favor of calling the original `SIMULATE_TARIFF_SCENARIO` directly.

## Bronze/Silver (pre-existing, unrelated to any single phase's scope)

**`int_hs_classified_raw` dormant schema-drift bug.** Surfaced during Phase 8's sanity-check `dbt build` — the first bare, unscoped build run since Phase 5; every build since (including all of Phases 6-9) used `--select` and never touched this model, so the bug sat undetected. Root cause: the physical table has 6 columns (including `predicted_hs_6`, `classification_status`) left over from Phase 5's one-time-run-then-renamed-into-place history, but the model's current SELECT only produces 4 columns, so dbt's incremental merge logic fails with `invalid identifier 'PREDICTED_HS_6'`. Not fixed in any phase so far because touching this model triggers a real ~$20 Cortex re-classification cost (per its own header warning) and a full rebuild-and-diff would be needed to confirm the fix doesn't change any already-validated classification output. Production path: investigate with `--full-refresh` in a deliberate, budgeted session (not as a drive-by fix), verify the rebuilt table's row count and a sample of predictions match the existing committed values before treating it as resolved.

## CI/CD

**Live dbt tests run only on manual `workflow_dispatch` trigger, not on every push.** This is a deliberate cost-control decision, not an oversight — running `dbt test` against live Snowflake on every commit would burn Cortex/warehouse credits on every push, including trivial doc-only commits. A judge checking "does CI include real dbt tests against live data?" will see the manual trigger and should read that as intentional budget discipline, not incompleteness. Production path: once a dedicated CI warehouse and credit budget are allocated (separate from the interactive-development `LADINGLENS_WH`), move to running on every push to `main`.

**Required GitHub Secrets for the `dbt-test-live` workflow** (not needed for `lint.yml` or `dbt-compile.yml`, which run without any Snowflake credentials):

## Observability

**Basic `AGENT_TRACES` logging in place; no automated quality scoring.** TruLens (`trulens-eval`) was evaluated directly and found unavailable on this account — installing it as a Snowflake UDF package fails because a transitive dependency (`psutil`) requires native code compilation, which the Python UDF sandbox doesn't support. The current observability panel reports latency and tool-usage distributions from real logged traces, but has no automated groundedness/context-relevance/answer-relevance scoring layer on top. Production path: either wait for a Snowflake-native equivalent capability, or score traces asynchronously outside Snowflake (e.g. a scheduled job pulling from `AGENT_TRACES` into an external evaluation service) rather than trying to run the scoring library inside the warehouse.

**`cost_credits_estimate` in `AGENT_TRACES` is an estimate, not a measured cost.** Derived from the token-usage metadata Cortex Agent responses include (input/output token counts, model name) against published per-token pricing, not from actual billing data. `SNOWFLAKE.ACCOUNT_USAGE.CORTEX_FUNCTIONS_USAGE_HISTORY` — the view that would provide ground truth — still returns zero rows as of Phase 10, well beyond the reporting lag Phase 5 first observed when investigating HS-classification Cortex spend. Production path: reconcile the estimate against `CORTEX_FUNCTIONS_USAGE_HISTORY` once/if it populates, and calibrate the per-token pricing constants if there's a persistent gap.
